# Módulo B — Backend y blockchain

## Alcance

Implementar B1–B5 con las interfaces de las secciones 7 y 8 del PRD sin modificar sus tipos públicos. B6 requiere un contrato funcional, ABI exportado por A, credenciales y fondos; no se ejecutan transacciones mainnet en esta entrega. No se modifican contratos, ABI compartido, UI ni agente.

## Dominio y cantidades

`Amount` sigue siendo un string decimal con hasta 18 decimales. Usar aritmética decimal exacta en el dominio, sin Number para importes; bigint queda dentro de los gateways. Se agrega `decimal.js` para la función pura de vesting, compatible con el navegador, y `server-only` para impedir importar claves y servicios de servidor en la UI. Validar montos no negativos dentro de uint256; top-ups y retiros deben ser positivos. Timestamps son segundos Unix enteros seguros; el reloj de la UI se trunca al segundo. La cancelación congela el devengado. El retiro disponible es min(devengado, depositado) menos retirado.

## Mock y demo offline

El mock reproduce lote atómico, permisos, fondeo, top-up, retiro, cancelación y balances. Inyectar el reloj para tests. Los balances, streams y metadata se conservan en un singleton por proceso; reiniciar el proceso reinicia la demo. Es una demo local: instancias serverless distintas no comparten esa memoria.

Sembrar una plataforma, dos trabajadores y streams activos con montos legibles. Las wallets y direcciones Belo del mock son ficticias, distintas de los placeholders de Supabase. Usar hashes `mock:...`, explorerUrl vacío y nota explícita de simulación. Las respuestas incluyen `X-Chain-Mode: mock|real` y `Cache-Control: no-store`.

## Servicio y API

Un servicio coordina un `StreamGateway` y un repositorio intercambiables. El modo mock nunca requiere Supabase ni RPC. El modo real exige configuración válida y nunca cae silenciosamente al mock.

- GET users devuelve exclusivamente DemoUser; GET streams y activity requieren userId y filtran por participante.
- POST streams usa payerId como identidad de creación; si además se envía userId debe coincidir. Las demás mutaciones requieren userId en body o query. Rechazar identidades contradictorias.
- Validar JSON, roles, destinatarios, ownership, rangos, límites de fondeo y retiro, y dirección Belo configurada antes de escribir.
- Los errores mantienen `{ error: string }`: 400 entrada inválida, 403 permisos, 404 recurso inexistente, 409 saldo/estado incompatible, 503 configuración o proveedor no disponible. No devolver claves, URLs RPC ni errores crudos de proveedores.
- Las rutas [id] usan params asíncronos de Next.js. Las mutaciones se serializan por proceso para evitar carreras locales entre lecturas, escrituras y registro de actividad; esto no reemplaza la validación del contrato.
- Registrar actividad visible tanto al pagador como al trabajador del stream. Los montos siguen siendo strings al leer Postgres.

## Persistencia y modo real

El repositorio Supabase usa service-role exclusivamente del lado servidor. Agregar una función SQL transaccional que registra conjuntamente los streams creados y sus actividades. Las cantidades numeric se leen como texto para evitar perder precisión JSON. No mezclar estado mock con la base real.

El gateway viem valida chainId 42161, token/contrato/direcciones y correspondencia entre clave y wallet demo. Usa el ABI que exporta A; mientras esté vacío, devuelve error de configuración antes de firmar. Simula, firma, espera receipts exitosos y obtiene IDs y valores de cancelación de eventos del contrato, filtrando por su dirección. Aprueba solo el fondeo necesario. Serializa transacciones por wallet en el proceso. Los tests usan clientes/RPC simulados, sin claves reales ni red.

Una transacción confirmada no puede deshacerse si falla la base: devolver un error explícito con su hash, sin reintentar automáticamente la operación onchain. Los timeouts posteriores al envío también indican el hash y que debe consultarse antes de repetir. La autenticación real, idempotencia distribuida y reconciliación automática quedan fuera de la demo.

## Validación

Tests de vesting (límites, precisión, cancelación, fondos parciales), mock (permisos, atomicidad, saldo, retiros y carreras), API (flujos y rechazos), persistencia y gateway real (approve, receipts, eventos y errores). Ejecutar lint, typecheck, build y una prueba HTTP local de crear, fondear, retirar y cancelar. Verificar la migración nueva en PostgreSQL temporal.
